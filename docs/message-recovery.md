# Message mutation recovery

`GET /api/v1/channels/{channel_id}/messages/recovery` returns an authorized, durable channel mutation range. It requires the same current `VIEW_CHANNEL` and `READ_MESSAGE_HISTORY` permissions as message history. The authenticated database-history epoch is included in every response; HTTP history-epoch validation also applies.

Query parameters are `after` (required), `through` (optional on the first page), `limit` (1–100, default 100), and `known_ids` (up to 100 comma-separated positive message IDs). Revisions are nonnegative decimal strings. The first page fixes `through`; subsequent pages retain it and use `next` as `after`. Each changed message has a unique revision, including each target of a bulk deletion.

A successful response includes `after`, `through`, `floor`, `next`, `complete`, `projection_head`, `changes`, and `states`. The delta range is `(after, through]`. `complete` means that this fixed range has been enumerated. It does not acknowledge a newer transport event or advance the client to `projection_head`.

Each change contains `revision`, `kind` (`create`, `update`, or `delete`), `message_id`, and `archived_message`. Plaintext is never copied to the archive. An encrypted create or body edit retains its original envelope, author ID, message/channel IDs, original delivery nonce, and timestamps, with `content` empty. These envelopes are for ordered Signal state recovery; their plaintext must not be projected as current messages. Deletes and metadata-only updates have no archived body.

`states` covers both changed IDs in this page and explicitly requested `known_ids`. A present state includes the current message and its exact `revision`; a deleted state explicitly proves absence in this authorized channel at `projection_head`. These message rows and `projection_head` are read under one short channel transaction lock. They may be newer than `through`. Attachment, author profile, and reaction decorations use their existing serializers and are not a historical snapshot of those separate resources. A client must version-filter these projections against later live changes. It must not infer deletion from absence in a paginated history list.

The database retains the newest 2048 mutation rows per channel. Pruning and raising `floor` are atomic with the message mutation. Encrypted envelopes, including deleted or superseded versions, exist only inside this bounded window. Message-row metadata updates also consume revisions. A client with `after < floor` receives HTTP 409 `MESSAGE_RECOVERY_GAP`, an explicit `floor`/`head`, and reason `retention` or `before_migration`; no successful cursor is returned. Existing messages are not backfilled with invented original encryption envelopes. A pre-upgrade nonempty channel has an explicit migration boundary. Corrupt or discontinuous retained rows also fail the request rather than acknowledging a truncated range.

Authenticated WebSocket READY/RESUMED and SSE READY carry `recovery_required: true`. WebSocket subscribes to live events before constructing the handshake. SSE preserves its live subscription across transport reconnects; an evicted, future, or event-bus-loss cursor sets `replay_gap: true` on READY and advertises the current transport head. No immediate invalid-session control frame cancels that recovery barrier. Healthy SSE replay advertises the original completed cursor before replay frames.

Clients must keep delivery and saved-receipt publication paused until their chosen durable range is journaled and their known message IDs have authoritative projections. Incoming live mutations remain held in order during this work. A fixed upper fence plus version-filtered buffered events permits catch-up to finish under continuous writes. Locked identities can journal the encrypted envelopes and tombstones before later processing Signal state. A floor gap requires explicit history review; it is never successful cryptographic recovery.

Message create/update/delete events carry exact `message_revision`; bulk deletion carries `message_revisions` keyed by each actually deleted ID. `channel_activity.revision` remains an activity head, not the identity of that event's mutation. A delayed publisher whose original mutation has already expired sets `recovery_required` rather than inventing a revision.

## Client integration and remaining verification

`AccountMessagingRuntime` begins with delivery paused, even when encrypted local storage has a matching saved epoch. `pauseAccountMessagingForRecovery(scope)` invalidates the connection lease and stops existing drivers at transport start/teardown. `acceptHandshake()` captures that lease before opening storage, journals a fixed fence for known cached/queued/receipt targets, and only then starts replacement drivers. Signal enrollment is independent of ordinary-channel encrypted device storage. Enrollment or a channel-specific recovery gap does not prevent other ordinary channels from completing their handshake.

`acceptGatewayMutation()` gates create/update/delete and each revision-ordered bulk target. It takes the same per-account/channel Web Lock as HTTP recovery before opening a vault transaction. An exact next revision can commit the archive, canonical authority, tombstone effects, and cursor together; a jump, missing revision, or `recovery_required` event fetches a bounded feed range first. A previously interrupted range keeps its original fence, with at most one additional range to reach the requested live revision. A second caller's known IDs/current-head request is never discarded merely because another range was already running. Gateway dispatch checks the captured connection lease again immediately before UI projection. A failed durable commit rejects checkpoint acceptance; already committed earlier bulk targets remain valid and replay is idempotent.

Locked identities retain archived envelopes in encrypted device storage. Unlock processes immutable archives in channel-revision order before legacy inbox records. Each ratchet/plaintext-cache transaction commits before its archive entry is retired. A failed envelope keeps later envelopes in that channel pending and prevents its sender from proceeding. Archived bodies are never displayed. Current-author decoration (anonymous accounts and the deleted-user `-1` projection) is separate from the immutable archive's numeric crypto sender identity.

`prepareChannelHistory()` gates HTTP history/pin reads; `filterDeletedMessages()` additionally audits every previously unknown returned ID at a fixed cursor, including IDs below the current cursor. Pagination omission is never deletion proof. Canonical tombstones suppress late HTTP, pin, and receipt results. A present body above the chosen fence appears only as a loading placeholder until the live/feed cursor reaches its revision; the prior ciphertext is removed from that placeholder so an old decrypt cannot restore stale text. Historical creation receipts are marked as already observed when a vault opens, and fresh receipt publication passes through the same authority filter. Decrypt/receipt continuations capture connection ownership before their first await and cannot publish across a pause/replacement.

A strictly unencrypted channel can use the authenticated head from a bound floor-gap response to audit known IDs without pretending to reconstruct a ratchet. This baseline never lowers an existing cursor. An encrypted gap remains an explicit recovery error. Permission-denied or unproven missing-channel responses retain saved work and block that channel; they do not create deletion receipts or tombstones. A database-history change retains old namespaces for explicit review rather than replaying old IDs/requests into the restored database.

Focused client tests cover protocol binding, cursor/authority atomicity, quota failure and reload, deleted starters with dependent envelopes, fixed-fence future edits, unknown stale HTTP rows, locked receive, transport replacement during storage opening, dispatch continuation ownership, and coalesced recovery callers. The new recovery path still requires combined current-server browser verification, including restart/replay eviction while a recipient misses an initial encrypted envelope. The prior first-DM browser checkpoint predates this feed activation. Group encryption, encrypted attachment/upload integration, and encrypted scheduling are separate unfinished producer adapters; this contract does not claim those paths are enabled.

Media keys are a separate contract and no longer touch the account identity at all. A call mints its own X25519 keypair (`client/src/lib/media/mediaKeyring.ts`) when a participant joins a media session and destroys it on leave; the public half is published on the media control plane (`SessionJoin` carries it, the relay copies it into the participant roster) and frame sender keys are wrapped per recipient against it, scope-bound so a room key and a screen-share key never share wrapping material. Both engines — browser and desktop — speak exactly this contract. The binding of a call key to an account is asserted by the server, the same authority that already asserts `users.public_key` through `GET /users/{id}/keys`; what the encryption guarantees is that the relay forwarding the media cannot read it, for every account rather than only for accounts that completed identity enrollment on the device they are calling from. A peer that published no call key is refused, loudly: there is no unencrypted media path. Because the keys live one call, they provide no archive, need no backup, and offer no portable recovery — and, like every key in the browser, no protection from code executing in the same origin.

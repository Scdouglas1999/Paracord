# Checkpoint: the window's own chrome, and one app id everywhere

Two owner asks on `d32b1749` (KDE Plasma Wayland, RTX 4080, 5120x1440 at 240 Hz):

1. The taskbar shows the generic "W" icon: KWin reported the window as
   `paracord-desktop` (the GTK program name), and no desktop entry is called
   that.
2. "Paracord as a slate of glass on your desktop": no grey title bar; the app
   draws its own chrome in the Index language. Later extended by the owner to
   Windows and macOS: the same look and behavior on every platform.

Branch `feat/index-ui` (worktree `~/Documents/Paracord-index`). Spec: the new
`docs/index-spec.md` §3.2.

## 1. One app id: `com.paracord.desktop`

The bundle identifier from `tauri.conf.json`, reverse DNS as freedesktop and
Wayland ask. No reason against it was found; the one obstacle is the Tauri
bundler, which always names the Linux entry after the product
(`Paracord.desktop`), handled below.

| Where | What now carries the id |
|---|---|
| Linux, Wayland | `xdg_toplevel.set_app_id("com.paracord.desktop")`: `glib::set_prgname` before GTK starts (`app_identity.rs`, first line of `run()`) |
| Linux, X11 | `WM_CLASS = "com.paracord.desktop", "com.paracord.desktop"`: the program name, and `gdk::set_program_class` after the builder has built (GTK up) and before the app runs (windows made). GDK overwrites a class set before its init with the capitalized program name, so it cannot go first |
| Linux, application name | `glib::set_application_name("Paracord")` (what the sound mixer shows) |
| Linux, window icon | `set_icon_list` with 32, 64, 128, 256, 512 from `icons/` (Tauri's default is the 32 px PNG, blurred in an X11 Alt+Tab); X11 `_NET_WM_ICON` checked: 32, 64, 128, 256 |
| Linux, desktop entry | `com.paracord.desktop.desktop`: `Icon=com.paracord.desktop`, `StartupWMClass=com.paracord.desktop`, `MimeType=x-scheme-handler/paracord;`, `Exec=… %u` with F2's spec quoting (`client/src-tauri/linux/`, generated by `deep_link_desktop::main_entry`; a test holds the packaged file equal to it) |
| deb, rpm | install that entry and `hicolor/{32,64,128,256,512}/apps/com.paracord.desktop.png` (`bundle.linux.*.files`). The bundler's forced `Paracord.desktop` is rendered from `linux/bundler-alias.desktop`: `Hidden=true`, so desktops treat it as absent and the app is listed once |
| AppImage | same files in the AppDir; `scripts/finalize-appimage.sh` now also replaces the root entry, root icon and `.DirIcon` with the app's (what integrators copy) and checks the repacked result. It no longer exits early when there are no Wayland libraries to remove |
| Windows | `SetCurrentProcessExplicitAppUserModelID("com.paracord.desktop")` at start. NSIS and MSI already stamp `{{bundle_id}}` on their shortcuts (Tauri bundler templates, checked in its source); the Inno script's two shortcuts now name `AppUserModelID: "com.paracord.desktop"`. Notifications use the identifier already |
| macOS | `CFBundleIdentifier` is the identifier; the release job now asserts it and that the bundled `.icns` is `icons/icon.icns` |

### The scheme folds into the main entry (F2 migrated)

`deep_link_desktop::register` (Linux, at every start), replacing the separate
handler entry:

1. Removes `~/.local/share/applications/paracord-desktop-handler.desktop` (what
   earlier versions wrote).
2. Finds the winning `com.paracord.desktop.desktop` in the XDG data dirs (user
   first, then `XDG_DATA_DIRS`).
   - Someone else's (a package, an installer; no `X-Paracord-Generated=true`
     mark) that declares the scheme: used as is, never rewritten.
   - Someone else's without the scheme: reported in the client log
     (`[desktop-entry] paracord:// is NOT registered: … does not declare …`),
     not patched.
   - None anywhere (bare binary, AppImage nobody integrated): the app writes
     its own, marked, with its icon at 256 and 512 in the user's hicolor
     (refreshing an `icon-theme.cache` if one exists), and rewrites it when its
     program moves.
3. `update-desktop-database` when the user directory changed;
   `xdg-mime default com.paracord.desktop.desktop x-scheme-handler/paracord`
   only when the current default differs.

F2's quoting (`exec_argument`, `exec_line`) and its tests are unchanged and run
on the new entry.

### The owner's existing local install: one-time steps (for the orchestrator)

The launcher `~/.local/bin/paracord` execs
`~/.local/share/paracord-client/bin/paracord-desktop "$@"`, so `%u` reaches the
app. After installing the new binary:

```sh
APPS=~/.local/share/applications
ICONS=~/.local/share/icons/hicolor
SRC=~/Documents/Paracord-index/client/src-tauri/icons   # or wherever this commit is checked out

cat > "$APPS/com.paracord.desktop.desktop" <<'EOF'
[Desktop Entry]
Type=Application
Name=Paracord
Comment=Chat, voice and video with your servers and friends
Exec=/home/scdouglas/.local/bin/paracord %u
Icon=com.paracord.desktop
Terminal=false
Categories=Network;InstantMessaging;Chat;
MimeType=x-scheme-handler/paracord;
StartupWMClass=com.paracord.desktop
EOF
rm -f "$APPS/paracord.desktop" "$APPS/paracord-desktop-handler.desktop"

for s in 32x32:32x32.png 64x64:64x64.png 128x128:128x128.png 256x256:128x128@2x.png 512x512:icon.png; do
  install -Dm644 "$SRC/${s#*:}" "$ICONS/${s%%:*}/apps/com.paracord.desktop.png"
done
rm -f "$ICONS/512x512/apps/paracord.png"
[ -f "$ICONS/icon-theme.cache" ] && gtk-update-icon-cache -f -t "$ICONS"

update-desktop-database "$APPS"
xdg-mime default com.paracord.desktop.desktop x-scheme-handler/paracord
kbuildsycoca6
```

Then: unpin and re-pin Paracord in the Plasma task manager (a pinned launcher
stores `applications:paracord.desktop`, which no longer exists), and change any
KWin window rule that matches the class `paracord-desktop` to
`com.paracord.desktop`. `desktop-file-validate` passes on that entry (checked
with the packaged copy, which differs only in `Exec=`). The app, finding this
entry (no generated mark, scheme declared), leaves it alone. The first launch
also writes `com.paracord.desktop.desktop` as the scheme default if the step
above was skipped. If the new binary is started before the steps, it writes its
own marked entry and icons under the same names; the steps then overwrite the
entry, and the app never touches it again.

### How

- **Config.** `tauri.conf.json`: `decorations: false`, `shadow: true`, still
  opaque. `tauri.macos.conf.json`: `decorations: true`, `titleBarStyle:
  Overlay`, `hiddenTitle`, `trafficLightPosition {20, 24}` (a test holds it
  otherwise equal to the base window).
- **Linux, the toplevel** (`window_chrome::undecorate`). Dropping tao's header
  bar alone left KWin drawing its own title bar (GTK 3 announces server-side
  decoration over `org_kde_kwin_server_decoration` for a window without a
  custom title bar, whatever `decorated` says; seen in the first nested run).
  The window now announces client-side mode on realize
  (`gdk_wayland_window_announce_csd`): `WAYLAND_DEBUG` shows KWin answering
  `mode(1)`, and the shot has no frame. No CSD style, no shadow margin, no RGBA.
- **The page** (`components/windowChrome/WindowChrome.tsx`,
  `lib/windowChrome/`, `styles/window-chrome.css`, mounted once in
  `AppProviders`). Marks `html[data-window-chrome|platform|state|focus|surface]`
  and draws the controls (frameless, not in full screen), Linux's resize edges
  and hairline (normal state only). The state follows the window's
  resize/focus events. The surface (`toolbar | sheet | call | fill`) comes from
  the Glass store and sets the controls' band; each surface reserves
  `--wc-reserve` at its right (with its old padding as the floor). The first
  run's bar sets a 64 band.
- **Drag** (`windowDrag.ts`): one document listener; `data-window-drag` =
  `""` (the element itself), `deep` (its subtree) or `false`; any control on
  the way (button, link, field, focusable, interactive role) stops it. Marked:
  the toolbar (deep), a 12 px band over the sidebar's top (40 on macOS), the
  first run's bar (deep), the sign-in pages' empty ground, the loading screen.
  Tauri's `data-tauri-drag-region` is no longer used: its double click always
  toggles maximize.
- **Double click** (`window_titlebar_double_click`, async): Linux reads GTK's
  `gtk-titlebar-double-click` (toggle-maximize, minimize, lower; "menu" and
  "none" do nothing, a page click has no event to place a window menu with);
  macOS reads `AppleActionOnDoubleClick` (and the older
  `AppleMiniaturizeOnDoubleClick`) at the moment of the click and takes it on
  release without movement, as macOS does; Windows toggles maximize.
- **Resize, Linux.** Eight invisible edges (5 px; corners an L of 14) call
  `startResizeDragging`, with resize cursors. The vendored
  `tauri-runtime-wry` no longer attaches its own press-to-resize handler on
  the GTK webview (5 px, no cursor; a second resize started by the same press
  would race the page's). Windows keeps the system's resize border (the
  runtime's top strip plus the shadow frame); macOS is decorated.
- **Close** calls `close()`, which the shell turns into hide-to-tray as before.
- **Permissions**: `start-dragging`, `start-resize-dragging`, `minimize`,
  `toggle-maximize`, `close` (a test holds them).
- **Windows, corners.** `DwmSetWindowAttribute(DWMWA_WINDOW_CORNER_PREFERENCE,
  DWMWCP_ROUND)` at setup; Windows 10 refuses it (logged, square corners).
  Windows draws no rounding when maximized or snapped.
- **Native video / full screen.** Untouched: the underlay still toggles the
  webview's transparency only while a surface exists; full screen hides the
  controls (the call keeps its own Exit).

### Rounded corners on Linux: measured, not shipped

A rounded corner on Linux needs the toplevel and the webview transparent all
the time. A bench page (Index ground, a selection bar and a card animating on
WebKit's compositor thread without pause) ran in two otherwise identical builds,
`transparent: false` and `transparent: true` with a 12 px rounded root, each
maximized in the nested KWin at a 239.9 Hz custom mode, `PARACORD_FRAME_TRACE=1`,
the last 10 s of presented frames (the nested KWin renders on the first DRM
device, the AMD iGPU, as in the frame-pacing passes):

| 5120x1440 (the owner's size) | Opaque (shipped) | Transparent (rounded) |
|---|---|---|
| Frames shown per second | **198** | 109 |
| Most common interval | 79% at 1 refresh | 80% at 2 refreshes |
| GTK paint of the window, median / p95 | **2.04 / 2.44 ms** | 3.71 / 4.08 ms |
| Commit to screen, median | **4.8 ms** | 8.3 ms |

At 2560x1440 both reach 240 commits a second (paint 0.41 against 0.78 ms);
the opaque build had 19% of its commits superseded before display, the
transparent one 1%, so the smaller size is not a clean comparison. At the
owner's size the transparent window halves the frame rate and nearly doubles
the paint: **square corners on Linux**. Windows 11 and macOS round natively at
no cost.

### Per platform

| | Linux | Windows | macOS |
|---|---|---|---|
| Title bar | none; the page's controls at top right | same | native traffic lights over the sidebar (top band 40) |
| Edge | 1px `--wc-edge` hairline (not maximized/full screen) | DWM border and shadow | native |
| Corners | square | rounded on 11 (DWM), not maximized/snapped | native |
| Resize | page edges, `startResizeDragging` | system border (runtime strip + shadow frame) | native |
| Snap / tile | KWin shortcuts and window rules (by `com.paracord.desktop` now), Meta+drag; drag-to-edge through the compositor's move | Aero Snap by dragging (the move is the system's), Win+arrows; the Windows 11 snap-layout flyout on hovering maximize is **not** available (see below); Win+Z opens it | native full screen and tiling (green button) |
| Double click | GTK's title bar setting | maximize/restore | the system setting |

**Windows 11 snap layouts on the maximize button.** The flyout appears only
when the button's area answers `WM_NCHITTEST` with `HTMAXBUTTON`. With
WebView2's windowed hosting (what wry uses) the mouse goes to WebView2's own
child window, so the app's window never sees that hit test over page content.
The known ways are WebView2 visual hosting with its non-client region API
(a rewrite of how wry hosts WebView2) or simulating Win+Z on hover (a hack that
fights the user's keyboard). Neither is shipped; Win+Z works.
